# 14. Доработки 27.09.2026: голосовые, пересылка, буфер обмена, услуги, метрики, CI/CD

Заказчик посмотрел CRM и задал шесть вопросов. Этот документ — ответ на каждый из
них в виде архитектуры: что делаем, как это будет работать, где могут быть грабли и
как проверяем, что их нет. Порядок работ и статус — в конце.

Главные правила этой итерации:

- **Всё сначала на локальном стенде.** Продакшен не трогаем, пока локально не
  прошли все проверки. Выкатка — отдельным шагом и только с подтверждения.
- **Проверяем на настоящем Telegram, но не на боевых номерах.** У Telegram есть
  тестовые серверы с тестовыми номерами `99966XYYYY` (код входа — цифра X пять раз).
  На них прогоняется вся отправка и приём: голосовые, альбомы, пересылка — без
  SIM-карт и без риска для рабочих аккаунтов.
- **Миграции базы только расширяющие** (новые таблицы и колонки, ничего не
  удаляется и не переименовывается). Тогда откат на прошлую версию кода после
  выкатки безопасен: старый код не видит новых колонок и работает как раньше.

## 0. Вопросы заказчика → решения

| # | Вопрос | Что делаем |

Найдено попутно и тоже закрывается (это дефекты, а не пожелания):

| Что | Почему важно |
|---|---|
| Голосовые клиентов не играют в Safari (iPhone, Mac) | Safari не умеет формат Ogg/Opus, в котором Telegram присылает голосовые |
| Видео в Safari не играет | Safari требует отдачу файла по частям (HTTP Range), сервер отдаёт целиком |
| Опасная раздача файлов | Файл `.html`, присланный клиентом, открывался бы как страница на домене CRM — готовая XSS-атака. Теперь опасные типы только скачиваются |
| Альбомы задваивались после перезапуска шлюза | Из нескольких сообщений альбома CRM запоминала одно, остальные при подтяжке истории приходили повторно |
| Текст длиннее 1024 символов с файлом не отправлялся | Лимит подписи Telegram 1024 — сообщение трижды падало и помечалось ошибкой |
| Видео уходило клиенту с превью 1×1 и длительностью 0:00 | Telethon без метаданных не знает размеров видео |
| Фото больше 10 МБ или 2560 px отклонялось Telegram | Нет автоматического уменьшения |
| Правки клиента не доходили до CRM | Событие правки отбрасывалось как дубль |
| Прочитали на телефоне — в CRM висит «непрочитано» | Не обрабатывалось прочтение входящих с другого устройства |
| Контакт, геопозиция, опрос от клиента — пустой пузырь | Не распознавались эти типы сообщений |
| Файл клиента больше 25 МБ — пустое сообщение без объяснения | Молча отбрасывался |

## 1. Как устроено сейчас (коротко)

```
Менеджер ─► api ─► (база: messages + outbox) ─► gateway ─► Telethon ─► Telegram ─► клиент
Клиент   ─► Telegram ─► Telethon (gateway) ─► inbound_service ─► база ─► WebSocket ─► экран
Файлы:   браузер ─► POST /files/upload ─► S3 (MinIO) ; gateway берёт из S3 и шлёт в Telegram
```

Эта схема остаётся. Меняется то, что происходит **с файлом по дороге**, и появляется
новый вид задания в очереди — «переслать».

## 2. Медиа-конвейер (фундамент для голосовых, буфера и пересылки)

### 2.1. Инструмент: ffmpeg в образе бэкенда

Чтобы Telegram показывал голосовое как голосовое, видео — с превью и длительностью,
а Safari мог проиграть голосовое клиента, файлы нужно **понимать и преобразовывать**.
Стандартный инструмент — ffmpeg (+ ffprobe). Ставится в образ бэкенда пакетом ОС;
образ вырастает на ~250 МБ, на диске сервера это несущественно.

Все вызовы ffmpeg — отдельным процессом с таймаутом и лимитом параллельности
(не больше 2 одновременно на процесс api), чтобы тяжёлый файл не занял оба ядра
сервера. Модуль — `app/services/media.py`.

### 2.2. Загрузка файла из CRM (браузер → сервер)

1. Файл приходит на `POST /files/upload` (или `POST /files/voice` для записи с микрофона).
2. Проверки: размер ≤ **200 МБ** (было 50), расширение из белого списка. Тип файла
   определяет **сервер** по расширению и по содержимому (ffprobe), а не браузер —
   браузер легко обмануть.
3. Файл пишется во временный файл потоком (не целиком в память) и изучается:
   - **картинка** → ширина/высота;
   - **видео** → ширина/высота/длительность + кадр-превью (JPEG) для Telegram;
   - **аудио** → длительность (+ название/исполнитель, если есть);
   - **голосовое** (с микрофона) → перекодируется в Ogg/Opus моно 48 кГц — ровно
     формат голосовых Telegram — плюс длительность и «волна» (100 значений 0–31).
4. Файл кладётся в хранилище; всё, что узнали, сохраняется **в метаданных самого
   объекта** хранилища. При отправке сервер читает эти метаданные оттуда, а не
   верит тому, что прислал браузер.
5. В браузер возвращается ключ загрузки + вид (фото/видео/аудио/голосовое/документ),
   размеры, длительность, волна — чтобы сразу показать правильное превью.

Белый список расширений расширен: к нынешним добавлены webm, wav, aac, opus, flac,
m4v, avi, mkv, 3gp, zip, rar, 7z, ppt/pptx, odt/ods/odp, rtf, csv, epub, fb2, djvu.
Исполняемые и «активные» файлы (exe, bat, sh, js, html, svg…) по-прежнему запрещены.

### 2.3. Раздача файлов (сервер → браузер): безопасность и iPhone

`GET /files/{id}`:

- **Показ в браузере только для безопасных типов**: картинки (кроме SVG), аудио,
  видео, PDF. Всё остальное — принудительное скачивание (`Content-Disposition:
  attachment`, тип `application/octet-stream`). Дополнительно `X-Content-Type-Options:
  nosniff` и `Content-Security-Policy: sandbox`. Это закрывает атаку «клиент прислал
  HTML-файл с JavaScript, менеджер открыл — скрипт работает от имени CRM».
- **Отдача по частям (HTTP Range, ответ 206)**. Без неё Safari не воспроизводит
  видео и аудио вовсе. Заодно большие видео больше не читаются в память сервера
  целиком: сервер берёт из хранилища только запрошенный кусок.
- **Вариант для Safari**: `GET /files/{id}?variant=m4a` — голосовое Ogg/Opus,
  перекодированное в AAC (который Safari понимает). Делается при первом запросе и
  кешируется в хранилище (`derived/…`). Плеер в интерфейсе указывает оба источника,
  браузер сам выбирает, что умеет: Chrome/Firefox берут оригинал, Safari — m4a.

### 2.4. Отправка в Telegram (шлюз)

Сообщение CRM с несколькими файлами превращается в правильную серию отправок:

| Что во вложениях | Как уходит в Telegram |
|---|---|
| Голосовое | Отдельным сообщением как **голосовое** (`voice_note`) с длительностью и волной |
| Фото/видео (jpg, png, mp4, mov) | Альбомом до 10 штук; видео — с размером, длительностью и превью |
| Музыка (mp3, m4a, …) | Альбомом аудио с длительностью, названием, исполнителем |
| Всё остальное | Документами (альбом документов до 10) с исходным именем файла |

- **Подпись** (текст сообщения) ставится к первому файлу, если она ≤ 1024 символов.
  Длиннее — текст уходит отдельным сообщением перед файлами.
- **Большое фото** Telegram не принимает — шлюз уменьшает его до 2560 px / 10 МБ
  (Pillow). Если Telegram всё равно отклонил фото, оно переотправляется документом:
  клиент получит файл, а не ошибку.
- HEIC/TIFF/BMP/WebP — документом (Telegram не принимает их как фото).
- Файл берётся из хранилища **во временный файл**, а не в память: 200 МБ видео не
  раздувает процесс шлюза.
- **Все** номера сообщений Telegram, получившиеся из одного сообщения CRM (альбом,
  текст отдельно), запоминаются (`messages.tg_extra_ids`). Подтяжка истории их узнаёт
  и не создаёт дублей. Для отметки «прочитано» берётся последний номер.
- Новые понятные ошибки: «Клиент запретил получать голосовые сообщения»,
  «Клиент заблокировал этот номер» — без бессмысленных повторов.
- Шлюзу при выкатке даётся 60 секунд закончить начатую отправку, а не 10
  (`stop_grace_period`) — иначе большой файл мог оборваться на середине.

### 2.5. Приём из Telegram (шлюз)

| Что прислал клиент | Как видно в CRM |
|---|---|
| Фото, документ | как сейчас |
| Голосовое | плеер **с волной**, играет и на iPhone |
| Видео, **кружочек** (video note), GIF | видео; кружочек — круглым; GIF — зацикленно без звука |
| Музыка | аудиоплеер с названием |
| Стикер | картинка стикера; анимированный — эмодзи стикера |
| Контакт | карточка «📇 Имя, телефон» |
| Геопозиция / место | «📍 Геопозиция» со ссылкой на карту |
| Опрос, кубик и т. п. | понятная строка («📊 Опрос: …», «🎲 5»), а не пустой пузырь |
| Неизвестный тип | «Сообщение этого типа CRM не показывает — откройте в Telegram» |
| Пересланное сообщение | подпись «Переслано от …» |
| Файл > 20 МБ | сообщение появляется сразу, файл докачивается в фоне («загружается…») |
| Файл > 200 МБ | «Файл N МБ — слишком большой для CRM, откройте в Telegram» |
| Клиент отредактировал сообщение | текст в CRM обновляется, пометка «изменено» |
| Клиент удалил сообщение | остаётся в CRM с пометкой «удалено в Telegram» (история важна для бизнеса) |
| Менеджер прочитал с телефона | непрочитанное в CRM гаснет |

Фоновая докачка переживает перезапуск шлюза: незавершённые загрузки подбираются
заново (до 5 попыток), неудача — видимая пометка с причиной, а не пустота.

## 3. Голосовые сообщения

### 3.1. Запись в CRM

- Кнопка микрофона появляется, когда поле ввода пустое (как в Telegram).
- Нажали → браузер спрашивает доступ к микрофону (один раз) → идёт запись:
  красная точка, таймер, уровень громкости. Кнопки: «Удалить» и «Стоп».
- После «Стоп» — прослушать перед отправкой, удалить или отправить.
- Запись идёт в том формате, который умеет браузер (Chrome — WebM/Opus,
  Firefox — Ogg/Opus, Safari — MP4/AAC). Сервер всё приводит к Ogg/Opus.
- Если микрофона нет, доступ запрещён или браузер не умеет записывать — понятное
  сообщение, как это исправить. Если браузер записывать не умеет вовсе — кнопки
  нет (правило «ни одной кнопки-обманки»).
- Голосовое можно отправить и служебной заметкой (для команды) — тогда оно
  остаётся внутри CRM.

### 3.2. Путь голосового

```
микрофон → MediaRecorder (webm/ogg/mp4) → POST /files/voice
  → ffmpeg: Ogg/Opus 48 кГц моно, 32 кбит/с, без тегов → длительность + волна
  → хранилище → превью в поле ввода → «Отправить»
  → сообщение (kind=voice) + outbox → шлюз → send_file(voice_note=True,
    DocumentAttributeAudio(duration, voice=True, waveform)) → у клиента голосовое
```

### 3.3. Ограничения Telegram, которые учтены

- Голосовое не может быть в альбоме — всегда отдельное сообщение.
- Клиент с Telegram Premium может запретить голосовые от не-контактов
  (`VOICE_MESSAGES_FORBIDDEN`) — менеджер увидит ровно эту причину.

### 3.4. Воспроизведение

Плеер показывает волну (как в Telegram), длительность, перемотку. Голосовые клиентов
приходят в Ogg/Opus — Chrome и Firefox играют сами, Safari получает AAC-версию (§2.3).

## 4. Буфер обмена

- **Вставка**: Ctrl/Cmd+V в поле ввода. Если в буфере картинка (скриншот) или файл —
  он прикрепляется к сообщению с превью. Если в буфере текст — вставляется текст.
  Особый случай: копирование ячеек Excel кладёт в буфер и текст, и картинку —
  вставляется текст (так ожидают). Копирование файла в Finder/Проводнике кладёт
  имя файла текстом и сам файл — прикрепляется файл.
- **Перетаскивание** файлов в окно чата — подсветка «Отпустите, чтобы прикрепить».
- **Превью** перед отправкой: миниатюры картинок, иконки файлов, плеер голосового,
  **прогресс загрузки** в процентах. Любое вложение можно убрать.
- **Копирование из CRM**: у каждого сообщения меню «⋯» — «Копировать текст»,
  «Копировать изображение» (для фото), «Скачать», «Переслать», «Выбрать», «Изменить»
  (для своих текстовых). В режиме выбора нескольких — «Копировать» склеивает текст
  в формате «Имя, 14:05: текст».

## 5. Сводка по синхронизации CRM ↔ Telegram

Всё из §2.4 и §2.5 плюс:

- Правки менеджера из CRM уходят в Telegram (было), правки клиента приходят в CRM (новое).
- Отметка «прочитано» в обе стороны (новое — прочтение с телефона).
- Дубли исключены на трёх уровнях: уникальный индекс номера сообщения, запоминание
  всех номеров альбома, повторная пересылка не создаёт повторных сообщений в очереди.

## 6. Пересылка

### 6.1. Сценарии

1. Переслать сообщение клиента (текст, фото, голосовое) другому клиенту или
   исполнителю (астролог, таролог — если с ним есть переписка на аккаунте).
2. Переслать материал (PDF с разбором, аудио) из одного чата в другой.
3. Переслать несколько сообщений разом.

### 6.2. Как выглядит

Меню сообщения → «Переслать» (или «Выбрать» → отметить несколько → «Переслать»)
→ окно: поиск чата по имени/ID, список недавних; переключатель **«Скрыть
отправителя»** (по умолчанию включён: клиент Б не должен видеть имя клиента А);
необязательный комментарий → «Переслать».

Служебные заметки не пересылаются (их нет в Telegram, и они не для клиента).

### 6.3. Как работает

```
POST /conversations/{куда}/forward
  { source_conversation_id, message_ids[], hide_sender, comment? }
```

- Права: оба чата должны быть видны сотруднику (иначе 404).
- В целевом чате создаются **новые исходящие сообщения** — по одному на каждое
  пересылаемое, с пометкой «переслано из чата …» (видна только в CRM). Вложения не
  копируются физически — новые записи ссылаются на тот же файл в хранилище.
- Как отправлять, решается автоматически:
  - **тот же аккаунт Telegram** и у всех сообщений есть номер в Telegram →
    настоящая пересылка Telegram одним запросом (`messages.forwardMessages`,
    `drop_author` = «скрыть отправителя»). Быстро, без повторной загрузки файлов,
    альбомы остаются альбомами;
  - **разные аккаунты** (или сообщение ещё не ушло в Telegram) → копия: текст и
    файлы отправляются заново от имени целевого аккаунта (переслать «чужое»
    сообщение из другого аккаунта Telegram технически не позволяет).
- Если настоящая пересылка не удалась по причине, которую повтор не исправит
  (исходное сообщение удалено в Telegram, запрет пересылки), шлюз сам переходит
  на копию — сообщение всё равно дойдёт.
- Пересылка считается ответом клиенту: останавливает таймер ожидания и закрепляет
  чат за менеджером, если он был ничей — ровно как обычный ответ.

### 7.1. Что на доске и в документах

Доска Miro: «Надо сделать справочник», «добавить услугу в оплату», «по прайсу 4 900 ₽»;
модель данных — таблица `services` (название, цена, описание, активна, порядок).
Отклонение от цены и «Сбросить» — на доске помечены как «не в текущей итерации»,
поэтому их не делаем; показываем только цену по прайсу.

### 7.2. Как будет работать

- **Справочник** «Профиль → Услуги и цены» (только руководитель): название, цена
  (можно пустую — «цена по договорённости»), описание-подсказка, активна, порядок.
- **Окно оплаты**: поле «Название услуги» стало выпадающим списком с поиском.
  Выбрали услугу — подставились название и цена (цену можно поправить).
  Своё название вписать по-прежнему можно — справочник помогает, а не запрещает.
- В позиции сделки запоминается, какая это услуга справочника, и цена по прайсу
  **на момент продажи**. Переименование или смена цены в справочнике старые сделки
  не меняет. Это же даёт статистику «продажи по услугам».
- **Подсказки из истории**: на странице справочника — названия, которые менеджеры
  уже вписывали в сделки, с количеством и типичной ценой, кнопка «Добавить».
  На продакшене это сразу покажет реальный перечень продаваемых услуг.

### 7.3. Что нужно от заказчика

Утверждённый список услуг и цен. До этого локально справочник заполнен демо-услугами,
на продакшене руководитель заполнит его сам (подсказки из истории помогут).

## 8. Метрики

### 8.1. Что нашлось в документах и чего нет

| Показатель | Источник | Было |
|---|---|---|
| Сумма и число продаж, прирост | Miro «Статистика» | есть |
| График продаж, дни/недели/месяцы | Miro | есть |
| Среднее время ответа, цель | Miro | есть |
| Чатов в работе, новых клиентов | Miro | есть |
| **Средний чек** | BRD 8.1, 8.3 | **нет** |
| **Конверсия счетов в оплату** (выставлено → оплачено) | BRD 2.1 (цель 2), 8.2 | **нет** |
| **Конверсия новых клиентов в покупку** | BRD 8.1 «конверсия в оплату» | **нет** |
| **Продажи по услугам** (кол-во, выручка, доля, конверсия) | BRD 2.1 (цель 5), 8.2 | **нет** |
| **Разрез по аккаунтам/направлениям** | ТЗ 01.09 «Расширенная аналитика по аккаунтам» | **нет** |
| **Доля ответов в пределах цели** | BRD 2.1 (цель 1: «100% ответов < SLA») | **нет** |
| **Просрочки** — ответы позже порога плашки (30 мин) | BRD 8.3 «SLA-нарушения» | **нет** |
| **Ждут ответа сейчас** | BRD 8.3 «Без ответа» | **нет** (был только в чатах) |
| **Таблица менеджеров**: + средний чек, конверсия, вовремя %, ждут ответа | BRD 8.3 | частично |

Из BRD не переносим то, чего нет в новой модели: возвраты (D-13), «потерянные
клиенты» и ручные нарушения (их нет на доске), кумулятивная воронка этапов 0–5
(воронка теперь — аккаунты Бот → Первые продажи → Допы; её аналитика упирается
в доп. продажи, которые делаются отдельно).

### 8.2. Формулы (добавляются в `03-business-rules.md` §10)

| Показатель | Формула | Время |
|---|---|---|
| Средний чек | сумма продаж / число продаж | по дате оплаты |
| Конверсия счетов | из сделок, **отправленных** клиенту в периоде, доля оплаченных (на сегодня) | по дате отправки |
| Конверсия новых клиентов | из клиентов с первым обращением в периоде — доля, у кого есть оплаченная сделка | по дате первого обращения |
| Продажи по услуге | сумма и число позиций в оплаченных сделках; доля от выручки | по дате оплаты |
| Конверсия по услуге | позиции в отправленных в периоде сделках → доля оплаченных | по дате отправки |
| Разрез по аккаунту | продажи, средний чек, новых диалогов, чатов в работе, среднее время ответа — по аккаунту диалога | как у общих |
| Ответили вовремя | доля ожиданий клиента в периоде, закрытых ответом не позже цели (15 мин) | по дате начала ожидания |
| Просрочки | ожидания, закрытые позже порога плашки (30 мин), плюс не закрытые и уже старше порога | по дате начала ожидания |
| Ждут ответа сейчас | диалоги, где последний клиент ещё без ответа | на сейчас |

Рабочие часы (если включены) действуют на все показатели скорости — одной и той же
функцией, что и сейчас. Роли — как у существующих показателей: менеджер видит свои,
руководитель — все и в разрезах. Руководитель не попадает в показатели скорости менеджеров.

Отдельно: запросы скорости ответа переписаны так, чтобы проходить только по диалогам
с активностью в периоде, а не по всей таблице сообщений — на миллионе сообщений это
разница между секундами и долями секунды. Результат обязан совпадать с прежним до
секунды — это проверяется.

## 9. CI/CD — автоматическая проверка и выкатка

### 9.1. Схема

```
git push ─► GitHub Actions
            ├─ линт бэкенда (ruff) ─────────────┐
            ├─ фронтенд: eslint, tsc, vitest ────┤
            └─ сборка прод-образов ─► интеграция: ├─► все зелёные?
               поднять стек из ЭТИХ образов,     │     │
               миграции, демо-данные, все        │     ├─ ветка main → образы в GHCR
               проверки verify_*, модульные      │     │   (ghcr.io/…:sha-коммита)
               тесты, «без Redis»                ┘     └─ выкатка на сервер
```

**Выкатка** (скрипт `deploy/deploy.sh` на сервере, запускается по SSH):

1. Проверка свободного места на диске.
2. Код на сервере переводится на выкатываемый коммит (грязные правки на сервере —
   стоп с понятной причиной, ничего молча не затирается).
3. Скачиваются **ровно те образы, что прошли проверку** (по номеру коммита).
4. Если в новой версии есть миграции базы — **сначала бэкап базы** (`backup.sh --db-only`).
5. `docker compose up -d --wait` — миграции, затем api/шлюз/планировщик/веб,
   ожидание healthcheck; перезапуск nginx.
6. Проверка здоровья снаружи: `https://домен/health`, главная страница, шлюз жив.
7. Успех → бэкап этой выкатки удаляется (он был страховкой на момент перехода),
   старые образы чистятся (последние 3 версии остаются для отката).
8. Неуспех → **автоматический откат** на прошлую версию образов (миграции назад не
   крутятся — они расширяющие, старый код с новой схемой работает), бэкап
   сохраняется, выкатка помечается красной в GitHub.

Ручной откат на любую версию — кнопкой «Run workflow» с номером коммита.
Параллельных выкаток не бывает (очередь `concurrency`).

### 9.2. Что нужно сделать вам (один раз)

1. Сгенерировать отдельный ключ для выкатки (инструкция в `docs/16-ci-cd.md`),
   открытый — на сервер, закрытый — в секреты GitHub.
2. Секреты репозитория: `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`,
   `DEPLOY_KNOWN_HOSTS`, `DEPLOY_PATH`.
3. Включить защиту ветки `main`: пуш только после зелёных проверок (рекомендация).

Проверено локально: весь CI-стек поднимается тем же `docker-compose.ci.yml`, что и в
GitHub, скрипт выкатки прогоняется на локальной копии прод-контура, включая откат.

## 10. Изменения схемы базы (одна расширяющая миграция)

| Таблица | Изменение | Зачем |

| 5 | Пересылка: API, шлюз, интерфейс | 1–4 |

| 7 | Метрики | 6 |
| 8 | CI/CD | все |
| 9 | Полный регресс, документация, отчёт | все |

Каждый этап закрывается только зелёными проверками своего и всех предыдущих этапов.

### Риски

| Риск | Что делаем |
|---|---|
| Тестовые серверы Telegram недоступны из сети | Модульные тесты с поддельным клиентом покрывают логику; живой прогон переносится на первый боевой номер под наблюдением |

| Большие файлы нагружают сервер | Лимит 200 МБ, потоковая передача, не более 2 перекодирований одновременно |
| Откат после миграции | Миграции только расширяющие — проверяется откатом на локальной копии |

## 13. Аудит 30.09.2026: проверка «руками» в браузере и доработки UX

Все пять вопросов заказчика проверены в настоящем браузере (Chromium с поддельным
микрофоном) на десктопе и телефоне, за руководителя и за менеджера. Найдено и
исправлено (только фронтенд, схема базы не менялась):

| Что было | Как стало |
|---|---|
| Голосовое можно было только остановить и проверить — отправка отдельным шагом | В полосе записи две кнопки: «Остановить и прослушать» и «Остановить и отправить» (как стрелка в Telegram) |
| Запись короче секунды уходила на сервер и падала красной рамкой без слов | Не отправляется; понятная подсказка «Запись слишком короткая…» |
| У голосового в списке вложений не было текста ошибки | Причина показывается под плеером |
| «Загрузка 100%» висела, пока сервер перекодирует голос | «Обработка…» |
| Вставка скриншота (Ctrl/Cmd+V) работала, только когда курсор в поле ввода | Работает в любом месте чата, если не открыто окно и не выбрано другое поле |
| Появились вложения — последние сообщения уезжали под поле ввода | Лента остаётся у нижнего края, пока человек сам не прокрутил вверх |
| В окне «Переслать» видно только «1 сообщение» | Предпросмотр: кто и что пересылается (до 3 строк, «и ещё N») |
| Esc не выходил из режима выбора сообщений | Выходит |
| Пустой справочник услуг: в окне оплаты обычное поле, непонятно почему | Подсказка: руководителю — ссылка «Профиль → Услуги и цены», менеджеру — «заполнить может руководитель» |
| Картинка, которая не открылась, оставляла пустой квадрат | Строка «Не удалось загрузить — нажмите, чтобы повторить» |
| Прирост в статистике «−11.6%» с точкой, остальное с запятой | Запятая везде |

Важно для выкатки: справочник услуг на проде пуст, пока руководитель его не заполнит.
Без этого менеджер видит обычное поле ввода — ровно то, на что жаловался заказчик.
Быстрее всего — «Профиль → Услуги и цены → Подсказки из истории → Добавить».
