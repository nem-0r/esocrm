# 02. Модель данных

PostgreSQL 16. Утверждена 2026-08-27 на основе доски Miro (`source/miro-extract.md`)
и решений `05-decisions.md`.

## Общие правила

- **Первичные ключи** — `bigint generated by default as identity`. UUID не берём: на таблице
  сообщений в миллионы строк случайные ключи портят локальность индекса. Внутренняя CRM
  за логином, скрывать порядок записей не от кого.
- **Номера, видимые пользователю**, совпадают с `id`: клиент `84271`, сделка `DEAL-1042`.
  Последовательности стартуют с «красивых» значений (`clients` с 80000, `deals` с 1000).
- **Деньги** — `bigint`, целые **копейки**. Дробных типов под деньги нет.
  Валидация: `> 0`, `<= 100_000_000_00` (сто миллионов рублей).
- **Время** — `timestamptz`, хранение в UTC. Даты в API — ISO `ГГГГ-ММ-ДД`.
- **Удаление** — логическое (`deleted_at`), кроме журнальных таблиц.
- **Внешние ключи** — `on delete restrict` везде, кроме журналов и вложений.
- **Разрезание таблиц по месяцам** в MVP не делаем. Причина: уникальное ограничение на
  разрезанной таблице обязано включать ключ разреза, и защита от дублей сообщений
  `(conversation_id, tg_message_id)` при этом перестаёт работать. Порог для планового
  разрезания — 50 млн строк в `messages`.

`birth_time` и `birth_time_approx` взаимно исключают друг друга: как только

считается до тех пор, пока нет именно точного времени: по части суток дома
гороскопа не построить.

Индексы: `telegram_id` (unique), `phone`, `first_contact_at`,
GIN `pg_trgm` по `display_name` и `phone` для поиска по подстроке.

**Уникальность `telegram_id` обеспечивается индексом в базе, а не проверкой в коде.**
При конфликте вставки система читает существующую запись и продолжает с ней.

### conversations

| Поле | Тип | Ограничения | Описание |
|---|---|---|---|
| id | bigint | PK | |
| client_id | bigint | FK → clients, not null | |
| account_id | bigint | FK → telegram_accounts, not null | |
| tg_chat_id | bigint | not null | |
| responsible_id | bigint | FK → users | Кто первым ответил |
| responsible_since | timestamptz | | |
| started_at | timestamptz | not null | |
| last_message_at | timestamptz | | Для сортировки списка чатов |
| last_client_message_at | timestamptz | | Начало отсчёта времени ожидания |
| last_manager_message_at | timestamptz | | |
| awaiting_reply_since | timestamptz | | Пусто = ответ дан |
| unread_count | integer | not null, default 0 | |
| is_blocked_by_client | boolean | not null, default false | |
| closed_at | timestamptz | | Диалог в этом аккаунте завершён, клиент ушёл дальше по воронке |
| created_at | timestamptz | not null | |

Ограничение: `unique (client_id, account_id)` — один диалог на пару клиент-аккаунт.
Индексы: `(account_id, last_message_at desc)`, `(responsible_id, last_message_at desc)`,
`awaiting_reply_since` (частичный, `where awaiting_reply_since is not null`), `client_id`.

**Время ожидания не хранится.** Считается как `now() - awaiting_reply_since`.
Поле `awaiting_reply_since` ставится при входящем, если ответа ещё не было, и обнуляется
при первом исходящем. Баннер «ждёт больше 30 минут» — это выборка по частичному индексу.

**Счётчики денормализованы** (`unread_count`, времена) и меняются событием, а не пересчётом
на каждый запрос: список чатов — самый горячий экран системы.

| Поле | Тип | Ограничения | Описание |
|---|---|---|---|
| id | bigint | PK | |
| conversation_id | bigint | FK → conversations, not null | |
| tg_message_id | bigint | | Пусто у служебных и пока в очереди |
| direction | enum | not null | `in`, `out` |
| author_kind | enum | not null | `client`, `manager`, `userbot`, `system` |
| author_id | bigint | FK → users | Только при `author_kind = manager` |
| kind | enum | not null | `text`, `photo`, `video`, `document`, `voice`, `service` |
| text | text | | |
| is_internal | boolean | not null, default false | Служебное: клиент не видит |
| status | enum | not null | `queued`, `sent`, `read`, `failed` |
| error_text | text | | |
| random_id | bigint | unique | Метка своего исходящего — см. ниже |
| reply_to_tg_id | bigint | | |
| sent_at | timestamptz | | |
| read_at | timestamptz | | |
| created_at | timestamptz | not null | |
| edited_at | timestamptz | | |
| deleted_at | timestamptz | | |

Ограничения: `unique (conversation_id, tg_message_id)` при `tg_message_id is not null`
(частичный уникальный индекс) — повторная доставка события Telegram не создаёт дубль.
`unique (random_id)` — повторная отправка с тем же ключом не создаёт второе сообщение.

Индексы: `(conversation_id, created_at desc)` — основной для листания переписки;
GIN по `to_tsvector('russian', text)` — поиск по содержимому; `(author_id, created_at)`.

**Как отличается менеджер от юзербота.** Перед отправкой CRM генерирует `random_id`
и записывает сообщение со статусом `queued`. Шлюз отправляет в Telegram именно с этим
`random_id` и получает от Telegram номер сообщения. Когда приходит событие об исходящем,
чей `random_id` нам неизвестен, — это отправил юзербот-воронка, и он записывается с
`author_kind = userbot`. Заложено с первого дня: задним числом это не восстановить.

**Статуса «доставлено» нет.** MTProto его не отдаёт. Часы — в очереди, одна галочка —
отправлено, две — прочитано, крестик — ошибка. Ровно как показывает сам Telegram.

### outbox

Очередь исходящих. Отдельно от `messages`, потому что у неё своя дисциплина повторов.

| Поле | Тип | Описание |
|---|---|---|
| id | bigint | PK |
| message_id | bigint | FK → messages, not null, unique |
| account_id | bigint | FK → telegram_accounts, not null |
| conversation_id | bigint | FK → conversations, not null |
| payload | jsonb | not null | Текст, вложения, ответ на сообщение |
| attempts | smallint | not null, default 0 |
| next_attempt_at | timestamptz | not null |
| locked_by | varchar(64) | | Какой процесс взял |
| locked_until | timestamptz | |
| status | enum | not null | `pending`, `sending`, `done`, `failed` |
| error_text | text | |
| created_at | timestamptz | not null |

Индекс: `(account_id, status, next_attempt_at)`.

**Правила очереди.** Забирается с блокировкой строки (`for update skip locked`) — два процесса
не отправят одно и то же дважды. Внутри одного диалога отправка строго последовательная,
иначе сообщения придут вперемешку. Ограничение частоты Telegram считается на аккаунт,
поэтому очередь тоже разбирается по аккаунтам. При `FloodWait` от Telegram `next_attempt_at`
сдвигается на время, которое вернул сам Telegram, а не на выдуманное.

Индексы: `(client_id, created_at desc)`, `(sold_by_id, paid_at)`, `(status, expires_at)`,
`(conversation_id, status)`, `payment_code`.

**Переходы состояний** — проверяются на переходе, а не на поле:

```
draft → awaiting → paid
        awaiting → cancelled   (причина обязательна)
        awaiting → expired     (по расписанию, при наступлении expires_at)
        expired  → cancelled   (причина обязательна)
```

Из `paid` и `cancelled` переходов нет. Состав сделки меняется **только** в `awaiting`
и только с указанием причины. В прошлой версии правило «оплаченную сделку нельзя менять»
обходили сменой статуса — поэтому проверка стоит на переходе.

При записи оплаты сделка блокируется `select ... for update`: параллельные операции по одной
сделке в прошлой версии разъезжались.

## 5. Прочее

### notes — заметки о клиенте

`id`, `client_id` FK, `author_id` FK, `text` not null, `created_at`, `deleted_at`.
Индекс `(client_id, created_at desc)`.

### templates — шаблоны сообщений

`id`, `title` varchar(255), `text` text not null, `owner_id` FK → users (пусто = общий),
`sort_order`, `is_active`, `created_at`, `deleted_at`.
Вставляются в поле ввода **дописыванием**, а не заменой текста.

### notifications

`id`, `user_id` FK not null, `kind` enum (`deal_paid`, `account_assigned`, `account_unassigned`,

## 6. Что закладывается под следующие этапы

Структура допускает без ломающей миграции:

- **Подписки** — таблицы `subscriptions` и `subscription_periods` со связью на клиента.
  Именно поэтому оплаченная сумма не хранится в клиенте одним числом, а выводится из сделок.
- **Возвраты** — таблица `refunds` со связью на сделку; в аналитике выручка станет
  «оплачено минус возвраты».
- **Рассрочка** — несколько платежей по одной сделке, таблица `deal_payments`.
- **Задачи** — таблица `tasks` со связями на клиента, сотрудника и сделку.
- **Справочник услуг** — `services`; `deal_items.name` останется снимком названия.
- **Дубли клиентов** — `merged_into_id` в `clients`.

Три поля заведены заранее и в MVP никем не заполняются — это осознанно, а не забытая работа:

- `conversations.closed_at` — закрывать диалог будет интеграция с воронкой,
  когда клиент переходит в следующий аккаунт. Своей кнопки «закрыть диалог» на доске нет,
  поэтому и в интерфейсе её нет.
- `attachments.telegram_file_id` — заполнит шлюз MTProto, когда начнёт принимать файлы.
- `clients.pdn_consent_*` — придут из бота воронки вместе с карточкой клиента; в CRM
  показываются в карточке, а руками их не проставить: согласие даёт клиент, не менеджер.
  Отозвать согласие на рассылку менеджер может — это просьба клиента, и она датируется.
