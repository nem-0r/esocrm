# 16. CI/CD: автоматическая проверка и выкатка

С 27.09.2026 обновление продакшена — не ручной `git pull` по SSH, а конвейер:
каждый пуш проверяется так же, как работает продакшен, и только зелёный `main`
уезжает на сервер. Здесь — как это устроено и что нужно сделать один раз.

---

## 1. Что происходит при пуше

```
git push ──► GitHub Actions (.github/workflows/ci.yml)
             ├─ Бэкенд · линт          ruff
             ├─ Бэкенд · модульные     pytest tests/unit (с ffmpeg)
             ├─ Фронтенд               eslint, tsc, vitest, прод-сборка
             └─ Интеграция             ─ сборка прод-образов (один раз)
                                       ─ тестовый стенд из ЭТИХ образов
                                         (docker-compose.ci.yml, демо-режим)
                                       ─ миграции, демо-данные
                                       ─ все проверки verify_* (deploy/ci-verify.sh)
                                       ─ работа без Redis
             если ветка main и всё зелёное:
             ├─ образы в реестр GHCR под номером коммита (sha-<коммит>)
             └─ выкатка (.github/workflows/deploy.yml → deploy/deploy.sh на сервере)
```

- На любой ветке и в пул-реквесте — только проверки. Выкатка — только `main`.
- Новый пуш в ту же ветку отменяет недоделанную проверку прошлого (кроме `main`).
- Две выкатки одновременно не идут никогда: вторая ждёт первую.
- `verify_robokassa` в CI не запускается: он создаёт настоящие счета в боевом
  магазине esoterra-pay. В тестовом стенде Робокасса выключена.

## 2. Что происходит на сервере (deploy/deploy.sh)

1. Проверка места на диске (нужно ≥ 5 ГБ) и файла `.env`.
2. Рабочая копия переводится на выкатываемый коммит. Если на сервере кто-то
   правил файлы из репозитория руками — выкатка останавливается и показывает,
   какие именно: молча затирать чужую правку нельзя.
3. Скачиваются **ровно те образы, что прошли проверки** (по номеру коммита).
   Реестр недоступен — образы собираются на сервере, как раньше.
4. Если в новой версии есть миграции — **сначала бэкап базы**
   (`backup.sh --db-only`: только база, без гигабайтов вложений).
5. Миграции, затем api, шлюз, планировщик, веб; перезапуск nginx. Если база
   новее выкатываемого кода (возврат на прошлую версию) — миграции пропускаются.
6. Проверка здоровья: api/web/nginx здоровы, шлюз Telegram работает и не
   перезапускается, `https://домен/health` и главная страница отвечают.
7. Успех — бэкап этой выкатки удаляется (он был страховкой на момент перехода),
   старые образы чистятся (последние 3 версии остаются для отката).
   Неуспех — **автоматический откат** на прошлую версию; бэкап остаётся,
   выкатка помечается красной в GitHub.

Миграции назад не откатываются. Правило для всех будущих миграций:
**только расширяющие** — новые таблицы и колонки с NULL или значением по
умолчанию; удаление и переименование — отдельной выкаткой позже, когда старый
код точно не нужен. Новое значение перечисления (тип Postgres) можно добавить,
но записывать его — только когда на проде уже стоит версия, которая его читает
(D-28; сторож в CI — `tests/verify_rollback_compat.py`). Тогда откат кода на
прошлую версию всегда безопасен.

## 3. Что сделать один раз

### 3.1. Отдельный ключ для выкатки

На своём компьютере:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/astra_deploy -C "astra-ci-deploy" -N ""
```

Открытый ключ — на сервер, в `authorized_keys` пользователя, от имени которого
идёт выкатка (он должен состоять в группе `docker` и иметь доступ к `/opt/astra`):

```bash
ssh-copy-id -i ~/.ssh/astra_deploy.pub <пользователь>@<сервер>
```

Отпечаток сервера — чтобы CI не подключился к подменённому хосту:

```bash
ssh-keyscan -t ed25519 <сервер>        # вывод — в секрет DEPLOY_KNOWN_HOSTS
```

Ключ отдельный намеренно: его можно отозвать, не трогая свой личный доступ.

### 3.2. Секреты в GitHub

Репозиторий → Settings → Environments → **New environment** `production` →
Environment secrets:

| Секрет | Что туда | Пример |
|---|---|---|
| `DEPLOY_HOST` | адрес сервера | `crm.example.ru` или IP |
| `DEPLOY_USER` | пользователь SSH | `deploy` |
| `DEPLOY_SSH_KEY` | содержимое `~/.ssh/astra_deploy` (закрытый ключ целиком) | `-----BEGIN OPENSSH PRIVATE KEY-----…` |
| `DEPLOY_KNOWN_HOSTS` | вывод `ssh-keyscan` из 3.1 | `crm.example.ru ssh-ed25519 AAAA…` |
| `DEPLOY_PATH` | каталог проекта (необязательно) | `/opt/astra` |
| `DEPLOY_PORT` | порт SSH (необязательно) | `22` |

В том же окружении можно включить **Required reviewers** — тогда каждая
выкатка будет ждать нажатия «Approve» в GitHub. Для начала это разумно.

### 3.3. Доступ сервера к репозиторию

Сервер делает `git fetch` сам. Если сейчас `git pull` в `/opt/astra`
работает — ничего делать не нужно. Если репозиторий приватный и доступа нет —
добавьте серверу **Deploy key** только на чтение (Settings → Deploy keys).

### 3.4. Защита ветки main (рекомендуется)

Settings → Branches → Add rule для `main`: «Require status checks to pass» —
отметить задачи «Бэкенд · линт», «Бэкенд · модульные тесты», «Фронтенд …»,
«Интеграция …». Тогда в `main` не попадёт ничего непроверенного.

### 3.5. Первая выкатка через CI

Файл `docker-compose.prod.yml` теперь знает имена образов из реестра. Первая
выкатка после этого изменения скачает образы под новыми именами; прошлые,
собранные на сервере, останутся для отката и уберутся следующими выкатками.

Перед первой выкаткой — пять минут проверок на сервере, от имени пользователя
выкатки:

```bash
cd /opt/astra
git status --short --untracked-files=no   # пусто: файлы репозитория на сервере не правили
git fetch origin && echo ок               # сервер сам достаёт код из GitHub
docker compose version                    # Compose v2.20 или новее
df -h /opt/astra                          # свободно не меньше 5 ГБ
id -nG | grep -qw docker && echo ок       # пользователь в группе docker
curl -fsS "https://$(grep -E '^DOMAIN=' .env | cut -d= -f2)/health"   # {"status":"ok"}
```

Последняя строка важна: выкатка проверяет здоровье с самого сервера по домену.
Если сервер не видит сам себя по своему домену, любая выкатка будет считаться
неудачной и откатываться.

Что увидят пользователи при выкатке: api, шлюз и веб перезапускаются — CRM
недоступна примерно минуту; шлюз перед остановкой дописывает начатую отправку
(до 60 с), а новые сообщения ждут в очереди и уходят после старта. Первая
выкатка этого релиза дополнительно снимает бэкап базы и применяет миграцию —
это секунды.

## 4. Откат вручную

GitHub → Actions → **Deploy** → Run workflow → номер коммита прошлой рабочей
версии (полный, 40 символов; есть в `deploy/.releases` на сервере и в истории
Actions). Образы последних версий лежат и на сервере, и в реестре.

Что происходит при возврате на прошлую версию:

- схема базы остаётся новой — выкатка видит, что база новее кода, и миграции
  не трогает (прошлый код с новой схемой работает, D-28);
- на версию **до автовыкатки** (например, ту, что стоит на проде сейчас) тоже
  можно вернуться: своего сценария выкатки у неё нет — берётся текущий, а образы
  собираются на сервере из её кода (несколько минут, как выкатывали раньше).

**После возврата не запускайте обычный `docker compose ... up -d`.** Он
запустит `migrate` прошлой версии, та не знает новую ревизию базы, падает — и
api за ней не поднимается. Перезапуск в этом состоянии — только так:

```bash
docker compose -f docker-compose.prod.yml up -d --no-deps api gateway scheduler web
```

Следующая выкатка новой версии возвращает всё в обычный режим.

## 5. Проверить всё локально, как в CI

```bash
make ci        # собрать прод-образы, поднять тестовый стенд, прогнать всё
make ci-down   # убрать стенд
```

Стенд — отдельный проект Docker (`astra-ci`) со своими томами и без открытых
портов: рабочие локальные данные и другие проекты он не трогает.

## 6. Хранилище файлов MinIO: образ больше не скачать

С осени 2025 MinIO не публикует бесплатные образы: `minio/minio` на Docker Hub
удалён, `quay.io/minio/minio` закрыт. На сервере образ скачан раньше
(`RELEASE.2025-09-07T16-13-09Z`) и работает; выкатка его не перекачивает.

Тестовый стенд CI собирает тот же выпуск из исходников — `deploy/minio/Dockerfile`
(внутри те же `minio` и `mc`, что в официальном образе).

Если образ на сервере потеряется (чистка диска, новый сервер), хранилище не
поднимется: `pull access denied for minio/minio`. Тогда собрать его на сервере под
тем же именем — данные в томе `minio-data` не трогаются:

```bash
cd /opt/astra
docker build -t minio/minio:latest deploy/minio        # 5–10 минут
docker compose -f docker-compose.prod.yml up -d --no-deps storage
```

## 7. План ресурсов под размер сервера (с 02.10.2026)

Выкатка (`deploy/deploy.sh`, шаг 3б) пересчитывает план ресурсов: `deploy/resource_plan.py` по
числу ядер и памяти сервера считает потолки памяти контейнеров, веса процессора и настройки
Postgres и пишет их в помеченный блок `.env`; `docker-compose.prod.yml` читает значения оттуда
(без блока — прежние). Изменились значения — `up -d` пересоздаёт только затронутые сервисы:
**база перезапускается на 10–30 секунд** (первая выкатка с планом сделает это один раз).
Не вышло или не прошли проверки здоровья — блок и значения возвращаются прежние.

После апгрейда тарифа сервера:

1. Перезагрузка сервера (контейнеры поднимутся сами; число процессов шлюза и api подстроится).
2. Потолки памяти и настройки базы — любым из способов: следующая выкатка; Actions →
   «Пересчёт ресурсов сервера» (сначала с галкой «dry run»); на сервере `./deploy/apply-resources.sh`.
3. Проверить: `https://<домен>/health`, в журнале шлюза «Поднимаю N процессов», в CRM
   (руководителю) нет полосы про устаревший размер сервера.

Выключить автоматику: `ASTRA_AUTOSIZE=off` в `.env`. Убрать блок — удалить строки между
`# >>> astra-resource-plan` и `# <<< astra-resource-plan` (compose вернётся к прежним значениям).
Расчёт «а если сервер станет такой»: `python3 deploy/resource_plan.py --cores 8 --ram-mb 32768`.
Автоматический пересчёт при каждой загрузке сервера — юнит systemd `deploy/astra-resources.service`
(включается отдельно: `sudo ./deploy/install-resources-service.sh`, по умолчанию не установлен).
