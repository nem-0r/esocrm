# Подключение личных Telegram-аккаунтов (юзерботов)

Документ отвечает на два вопроса: **как это устроено** и **что нужно сделать,
чтобы менеджеры начали переписываться с клиентами из CRM**.

Код контура готов целиком. Не хватает трёх вещей, которые нельзя написать
кодом: ключей приложения Telegram, самих номеров и прокси.

---

## 1. Почему юзербот, а не бот

Клиенты пишут на личные номера, к которым привыкли. Бот такую переписку не
видит — он получает только то, что написали ему самому. Поэтому CRM входит в
аккаунт **второй сессией**, как ещё одно устройство: телефон владельца
продолжает работать как раньше, а мы получаем те же сообщения параллельно и
можем отвечать.

Отсюда всё остальное:

- сессия равна полному доступу к аккаунту, поэтому хранится зашифрованной;
- Telegram считает нас обычным клиентом и применяет обычные ограничения —
  их надо соблюдать, а не обходить;
- если владелец выйдет из всех сеансов на телефоне, наша сессия тоже умрёт,
  и это увидит руководитель на экране «Аккаунты».

## 2. Как устроен контур

```
Менеджер в CRM
      │  пишет сообщение
      ▼
   API (FastAPI) ──► таблица outbox в PostgreSQL   ← очередь, переживает перезапуск
      │                        ▲
      │ команды через Redis    │ порядок внутри диалога: conversation_id, id
      ▼                        │
   Шлюз (отдельный процесс) ───┘
      │  держит живые соединения MTProto
      ▼
   Telegram ──► входящие события ──► приём (inbound) ──► PostgreSQL ──► события в интерфейс
```

Четыре части и зачем каждая:

| Часть | Файл | Отвечает за |
|---|---|---|
| Аренда аккаунтов | `app/gateway/lease.py` | какой процесс держит какой аккаунт; процесс пропал — аккаунт подхватит соседний |
| Очередь исходящих | `app/gateway/runner.py` | отправка по порядку, повторы, перенос при FloodWait |
| Канал команд | `app/core/command_bus.py` | «запроси код», «подтверди код», «подтяни историю», «отметь прочитанным» из API в тот процесс, который держит аккаунт |
| Приём | `app/services/inbound_service.py` | единственная дверь для входящих: дедупликация, карточка клиента, счётчики, события |

### Почему вход идёт через канал команд, а не напрямую из API

Код подтверждения принадлежит **тому соединению**, которое его запросило.
Если API запросит код в одном процессе, а подтвердит в другом (а в проде
процессов API несколько), Telegram ответит «код недействителен». Поэтому API
просит шлюз, а шлюз держит соединение от запроса кода до подтверждения.

Побочная польза: **строка сессии не покидает шлюз**. Он шифрует её и кладёт
в базу сам, наверх возвращает только имя и идентификатор аккаунта — полный
доступ к чужому Telegram не путешествует по Redis и не оседает в логах.

### Что делает приём входящего

Один и тот же путь для четырёх источников — живое сообщение, ответ менеджера
с телефона мимо CRM, рассылка воронки и подтяжка истории:

1. **Дедупликация.** Опора — уникальный индекс `(conversation_id, tg_message_id)`.
   Telegram переприсылает события при переподключении, а история пересекается
   с живыми сообщениями — дубля не будет.
2. **Своё исходящее опознаётся по `random_id`.** CRM генерирует его перед
   отправкой. Сообщение с нашим random_id — уже записанное, ему проставляется
   номер в Telegram. Исходящее с чужим — воронка или ответ с телефона: пишем
   как `userbot`, автора не выдумываем.
3. **Карточка клиента и диалог заводятся сами**, `access_hash` сохраняется.
4. **Счётчики.** Ожидание ответа начинается с первого сообщения без ответа,
   а не с последнего. История (`live=False`) не поднимает непрочитанные и не
   шлёт уведомлений — иначе первое подключение завалило бы менеджеров.

### `access_hash` — то, на чём ломаются самодельные интеграции

Это не свойство человека, а пропуск, выданный **конкретному аккаунту**. Хэш,
полученный аккаунтом А, у аккаунта Б не работает. Поэтому таблица
`telegram_peers` ключуется парой «аккаунт + собеседник». Без сохранённого
пропуска после перезапуска нельзя ответить тому, кто не попал в свежий список
диалогов, — переписка выглядит живой, а отправка молча не работает.

## 3. Что нужно получить до подключения

| Что | Где взять | Комментарий |
|---|---|---|
| `api_id` и `api_hash` | my.telegram.org → API development tools | Одна пара на всю установку. Заводится на номер, к которому есть доступ |
| Номера менеджеров | у компании | Тот самый номер, на который пишут клиенты |
| Доступ к телефону при входе | у владельца номера | Код придёт в Telegram на его устройство |
| Облачный пароль | у владельца | Если на аккаунте включена двухфакторная защита |
| Мобильные прокси | закупка | По одному на аккаунт, решение D-21 |
| Резервный номер | купить заранее | Чтобы первое подключение проверить не на боевом аккаунте |

### Про прокси — не перестраховка

Несколько личных аккаунтов, входящих с одного серверного адреса, — типичная
картина спама с точки зрения Telegram. Свежие аккаунты с такого адреса
блокируют быстрее всего. Нужны **мобильные** прокси (не датацентровые),
по одному на номер, с постоянным адресом. Формат в настройке
`TELEGRAM_PROXY`: `socks5://логин:пароль@адрес:порт`.

Сейчас значение одно на установку. Поаккаунтные адреса — небольшая правка
(поле в таблице аккаунтов), делается вместе с закупкой: раньше её негде
проверить.

## 4. Порядок подключения

1. **Выключить демо-режим.** В `.env`: `DEMO_MODE=false`, заполнить
   `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`, при необходимости `TELEGRAM_PROXY`.
   Перезапустить api и gateway.
2. **Первый аккаунт — резервный номер, не боевой.** «Аккаунты» → «Подключить»:
   название, номер, ступень воронки.
3. **«Запросить код»** — код придёт в Telegram на устройство владельца номера.
   Ввести в CRM. Если включён облачный пароль, интерфейс спросит его вторым шагом.
4. **История подтянется сама** с даты из настроек (`history_sync_from`,
   по умолчанию 1 января 2026). Ход виден на экране аккаунтов; на аккаунте с
   тысячами диалогов это минуты, а не секунды.
5. **Проверить связку в обе стороны:** написать с другого телефона на этот
   номер — сообщение должно появиться в CRM за секунды; ответить из CRM —
   прийти на телефон.
6. **Назначить менеджеров** на аккаунт. До этого момента чаты видит только
   руководитель.
7. **Повторить для боевых номеров** — по одному, с паузой в несколько часов
   между подключениями.

## 4а. Сквозной сценарий: от кода до первого ответа

Что именно происходит по шагам — чтобы было видно, где данные и кто их видит.

| Шаг | Что делает человек | Что делает система |
|---|---|---|
| 1 | Руководитель: «Подключить», вводит название, номер, ступень воронки | Заводится строка аккаунта, статус «не подключён». Ключи приложения берутся из настроек сервера |
| 2 | Нажимает «Получить код» | API просит шлюз; шлюз открывает соединение с Telegram и запрашивает код. Соединение остаётся открытым — код принадлежит ему |
| 3 | Владелец номера диктует код из Telegram, руководитель вводит его | Шлюз подтверждает вход, **шифрует строку сессии и сам кладёт её в базу**. Наверх уходит только имя аккаунта и его id |
| 3а | Если на аккаунте облачный пароль — интерфейс спросит его вторым шагом | Тот же шлюз, то же соединение |
| 4 | Ничего | Автоматически стартует подтяжка переписки с даты из настроек. Идёт фоном, ход виден на экране аккаунтов |
| 5 | Ничего | Каждый диалог: заводится карточка клиента, создаётся диалог, сохраняется `access_hash`, пишутся сообщения. Счётчики непрочитанных и таймеры ожидания **не** трогаются — это история, а не новые обращения |
| 6 | Руководитель назначает менеджера на аккаунт | Если менеджер на аккаунте один, все диалоги этого аккаунта закрепляются за ним. Если несколько — диалоги остаются в общей очереди |
| 7 | Клиент пишет в Telegram | Событие приходит в шлюз за секунды: сообщение в базу, счётчик непрочитанных +1, начинается отсчёт ожидания, событие уходит ответственному менеджеру и руководителям |
| 8 | Менеджер открывает чат в CRM | Непрочитанные гаснут, плашка ожидания гаснет, в Telegram у владельца номера тоже снимается непрочитанное |
| 9 | Менеджер отвечает | Сообщение попадает в очередь `outbox`, шлюз отправляет его от имени аккаунта, статус меняется на «отправлено», потом на «прочитано». Если диалог был ничейным — менеджер становится ответственным |
| 10 | Клиент отвечает с телефона менеджера (мимо CRM) | Сообщение всё равно попадает в CRM: помечается как исходящее без автора, ожидание клиента снимается |
| 11 | Менеджер выставляет счёт | Уходит текст со ставкой, реквизитами и кодом платежа. Оплата подтверждается вручную, с номером чека |

**Что видит менеджер.** Только диалоги, где он ответственный, плюс ничейные на
своих аккаунтах — их можно взять в работу, ответив. Чужой закреплённый диалог
для него не существует: ни в списке, ни в поиске, ни в карточке клиента, ни в
материалах, ни в живых событиях. Проверяется автоматически.

**Что видит руководитель.** Всё, включая аккаунты этапа «Бот», и может передать
любой диалог другому менеджеру — тогда он мгновенно пропадает у прежнего и
появляется у нового.

## 5. Правила эксплуатации, которые снижают риск блокировки

- **Не подключать пачкой.** Пять номеров за час с одного сервера — верный
  способ потерять все пять.
- **Не рассылать из CRM.** Продукт для переписки; массовые рассылки делает
  воронка со своей стороны и со своими рисками.
- **FloodWait не обходить.** Telegram называет срок ожидания; повтор раньше
  срока продлевает запрет. Очередь уже переносит отправку ровно на названное
  время — руками не ускорять.
- **Не входить в аккаунт из CRM и из «сомнительных» клиентов одновременно.**
  Чем обычнее выглядит устройство, тем спокойнее.
- **Держать телефон владельца рабочим.** Аккаунт, где активна только серверная
  сессия, выглядит подозрительнее живого.

## 6. Что произойдёт при сбоях

| Событие | Что видно | Что делать |
|---|---|---|
| Процесс шлюза упал (в т.ч. плановый перезапуск при выкатке) | сообщения копятся в очереди, отправка встала | соседний процесс подхватит аккаунты за ~30 секунд, очередь разберётся сама. Входящие, пришедшие за это время, тоже не теряются: при подключении аккаунта заново шлюз сам подтягивает недавнюю историю от `last_activity_at` (`gateway/handlers.py::catch_up`) — вручную нажимать «Подтянуть историю» не нужно |
| Redis недоступен | не работают кнопки подключения и живые обновления | переписка и сделки не страдают; поднять Redis |
| Сессия отозвана владельцем | аккаунт «требует внимания», причина в карточке | «Переподключить» в карточке аккаунта |
| FloodWait | отправка отложена, в журнале записано на сколько | ничего; ждать |
| Клиент заблокировал аккаунт | ошибка отправки в переписке | ничего; это состояние клиента |

## 7. Чего в контуре ещё нет

Честный список, чтобы не было сюрпризов:

- **Групповые чаты не поддерживаются намеренно.** Диалог = «клиент + аккаунт»;
  группа сломала бы это правило.
- **Реакции и редактирование сообщений** принимаются как обновление текста,
  отдельной истории правок нет.
- **Голосовые не расшифровываются** — сохраняются файлом.
- **Файлы больше 25 МБ** не скачиваются к себе: сохраняется факт сообщения.
- **Поаккаунтные прокси** — одно значение на установку (см. выше).
- **Автоответ вне графика** не делается: график сотрудника показывает, кто на
  смене, но сам за него не отвечает.

## 8. Как это проверено без живого аккаунта

`make verify` гоняет `tests/verify_gateway.py` — 22 проверки, которые проходят
весь путь, кроме самого Telegram: команда из API уходит через Redis, шлюз её
исполняет, приём пишет в PostgreSQL. Проверяется, что входящее создаёт карточку
клиента и диалог, что повтор события не создаёт дубль, что `access_hash`
сохранён, что ответ с телефона снимает ожидание, а подтяжка истории не поднимает
счётчики.

Заменится источник событий — демо-провайдер на MTProto. Всё, что после
источника, останется тем же кодом.
