# 18. Замечания тестировщика (PDF от 11.10.2026): решения и спецификация

Источник: `CRM-zamechaniya.pdf` (BUG-01…10, L1…L6, «Решить»). Разбор каждого пункта по коду и по
прод-данным сделан 11.10.2026; здесь — **что именно делаем и как**. Код важнее Miro: Miro местами устарел.

## Решения (ADR-черновик; перенесено в `05-decisions.md` — актуальная редакция там)

**D-34. Одно определение «ждёт ответа дольше порога».** «Ждёт» = `awaiting_reply_since` не пуст и старше порога
(`awaiting_banner_minutes`, учёт рабочих часов как сейчас). Баннер в списке чатов, плитка «ждут ответа сейчас ·
N дольше 30 мин» в статистике и фильтр «Ждут >30 мин» считают **одно и то же число** по одной области видимости
(руководитель — всё; менеджер — свои и ничейные на его аккаунтах). «Просмотрено» (`awaiting_seen_at`) больше не
убирает чат из баннера и плитки — оно остаётся только для значка на строке чата и для «Взять первого».
Просмотр руководителем (admin) **не** ставит «просмотрено» и не гасит напоминание менеджеру. Клик по баннеру
включает фильтр «Ждут >30 мин» (виден, снимается крестиком). Это отступление от ТЗ 01.09 п. 2.1 («баннер гаснет, когда
менеджер открыл чат») ради требования «одно число везде»; вернуть можно одной правкой хелпера.

**D-35. Поиск везде одинаковый.** Один модуль сопоставления для глобального поиска, раздела «Клиенты» и списка
чатов: запрос нормализуется (нижний регистр, ё→е, лишние пробелы, ведущий `@`), делится на слова, **каждое слово
должно найтись** (И) хотя бы в одном из: `display_name`, `tg_first_name`, `tg_last_name`, `tg_username`, телефон
(по цифрам), числовой ID клиента. Результат везде показывает имя по лестнице `display_name` → «имя фамилия из Telegram»
→ `@username` → `telegram_id` (готовая `Client.name`), плюс `@username` и телефон, если есть. Транслитерация
(«Ксения» ↔ «Ksenia») — отдельная будущая фича, не входит. История поиска (L4) пишется только по явному действию
(Enter или клик по результату), без дублей (регистр и пробелы не различаются), новая запись поднимается наверх.

**D-36. Превью чата показывает статус последнего исходящего сообщения, как в Telegram:** часы — отправляется;
одна галочка — отправлено; две — прочитано; красный «!» — не доставлено. Для входящего последнего сообщения значка нет.
Иконки те же, что в пузыре сообщения (общий компонент). Обновляется в реальном времени по событиям сообщений.

**D-37. Аккаунт без связи.** Когда статус аккаунта `error`/`disconnected`: (а) отправка из CRM отклоняется сразу
понятной ошибкой 409, а не через ~35 с и три попытки; в интерфейсе поле ввода выключено с пояснением; (б) в чате
баннер: менеджеру «Аккаунт «X» отключён — сообщения не уходят. Сообщите руководителю», руководителю то же и кнопка
«Переподключить»; (в) `SessionLost` в шлюзе — окончательная ошибка, без повторов; (г) при переходе аккаунта в `error`
создаётся уведомление `account_error` руководителям и менеджерам аккаунта (один раз на переход). Значение enum
`account_error` в базе уже есть (D-28 не нарушается).

**D-38. Забыли пароль.** Почты в системе служебные (писем нет), поэтому сброс — через руководителя: кнопка «Сбросить
пароль» в карточке сотрудника выдаёт одноразовую ссылку на 24 часа (токен хранится хешем, в отдельных колонках, не в
колонках приглашения), сотрудник сам задаёт новый пароль, все его сессии и блокировка входа сбрасываются.
Для самого руководителя, если забыл пароль, — команда на сервере `python -m app.cli reset-password`. На странице
входа честная подсказка вместо мёртвой кнопки «Забыли пароль?». **Вход через Google не делаем сейчас:** нужны
настоящие почты сотрудников, проект в Google Cloud и ключи (даёт только владелец), а пока почты служебные — кнопка
работать не будет. Вернёмся, когда будут реальные почты; тот же механизм ссылки подойдёт и для отправки письмом.

**D-39. «Месяц» одинаков в Оплатах и Статистике** — календарный (с 1-го числа); под переключателем периода
всегда подпись диапазона дат. Неделя и квартал уже совпадают и не меняются.

## Правила для всех исполнителей

- Роли `admin`/`manager` (observer убран, D-16). Никаких кнопок-обманок: элемент в интерфейсе работает или его нет.
- Тексты интерфейса — по-русски, в стиле существующих; доступность (`aria-label`, `role`), телефон и компьютер,
  тёмная тема, существующие компоненты из `frontend/src/shared/ui`.
- Миграции только расширяющие (D-28). **Единственная новая миграция — сброс пароля.** Остальным: миграция нужна —
  остановись и сообщи.
- Бэкенд и фронтенд синхронны: контракт API не ломаем (старая сборка фронтенда должна пережить новый бэкенд, откат
  на прошлую версию кода — на новую схему). Параметризованный SQL; ничего не логировать из секретов.
- Тесты обязательны для всего, что меняется: модульные (`backend/tests/unit`, `frontend/src/**/*.test.ts`) и, где
  нужна база/API, набор `backend/tests/verify_<область>.py` по образцу существующих (`tests/support.py`).
- Запуск: бэкенд — `docker exec astra-crm-api-1 sh -c 'cd /app && python -m pytest tests/unit -q -p no:cacheprovider'`
  и `ruff check app tests/unit`; фронтенд — `cd frontend && npx tsc -b && npm run lint && npx vitest run`.
  Наборы `verify_*` пишут в общую dev-базу — запускать только под замком:
  `L=/private/tmp/claude-501/-Users-mac-tg-crm/verify.lock; until mkdir $L 2>/dev/null; do sleep 5; done; trap 'rmdir $L' EXIT; …`.
- Не коммитить и не менять `deploy/`, `docs/` (заметки для документации — в отчёте), чужие области.
