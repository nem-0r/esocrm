## 1. Состав системы

| Компонент | Технология | Роль |
|---|---|---|
| `web` | React 19 + TypeScript + Vite | Один сайт на все устройства |
| `api` | Python 3.12 + FastAPI | REST, WebSocket, права, аналитика |
| `gateway` | Python 3.12 + Telethon | Сессии Telegram, приём и отправка |
| `scheduler` | Python 3.12 + APScheduler | Сроки сделок, предагрегаты, чистка |
| `db` | PostgreSQL 16 | Единственный источник правды |
| `cache` | Redis 7 | Живые события, онлайн-статус, лимиты частоты |
| `proxy` | nginx | HTTPS, статика, проксирование |
| `storage` | S3-совместимое | Вложения и материалы; локально — MinIO |

**Модульный монолит + отдельный шлюз.** Шлюз вынесен, потому что держит долгие соединения,
ловит ограничения Telegram и переживает обрывы. Внутри веб-приложения его заминка тормозила бы
интерфейс, а перезапуск сайта рвал бы сессии всех аккаунтов.

**Ни один процесс ничего не хранит на своём диске.** Сессии Telegram — в базе (зашифрованы),
файлы — в объектном хранилище, состояние — в базе. Любой процесс одноразовый: убил, поднял,
ничего не потерялось.

**Шлюз сам подстраивается под железо контейнера.** Число процессов внутри `gateway` считается
при каждом старте по видимым ядрам, а не задаётся руками — подробности и обоснование в
`docs/13-adaptive-gateway.md`. Здесь — только контракт (§2 ниже), там — почему он устроен так.

**Потеря Redis не должна ничего ломать** — максимум страница один раз обновится сама.
Всё, что нельзя терять, живёт в PostgreSQL.

## 2. Как шлюз распределяет аккаунты

Контейнер `gateway` один, но внутри него — несколько независимых процессов ОС: сколько
именно, решает `app/gateway/topology.py` по числу ядер, видимых контейнеру, при каждом
старте (ядра минус одно про запас). Апгрейд сервера не требует трогать конфигурацию —
следующий перезапуск контейнера сам поднимет больше процессов. Полное обоснование —
`docs/13-adaptive-gateway.md`.

Дальше для каждого процесса — то же самое, независимо от того, что рядом работают такие же:

1. Процесс при старте пишет себя в `gateway_workers` со случайным `id` и вместимостью.
2. Каждые 10 секунд обновляет `heartbeat_at` и продлевает `lease_until` своих аккаунтов на 30 секунд.
3. Если держит меньше вместимости (сама вместимость на заходе может быть урезана, если хост
   занят — `app/gateway/load.py`) — забирает свободные аккаунты (`lease_until < now()` или
   `null`) через `select ... for update skip locked`.
4. Процесс пропал — аренда истекла — через 30 секунд аккаунт подхватил соседний
   и поднял сессию из базы. Супервизор контейнера (`app/gateway/worker.py`) обычно
   успевает поднять замену процессу гораздо раньше — за секунды, не дожидаясь протухания.

Добавление мощности = более крупный сервер под тем же контейнером, либо ещё один такой
же контейнер на другой машине. Ручной перенастройки числа процессов нет ни в том, ни в
другом случае.

## 3. Путь сообщения

**Входящее.** Telethon отдаёт событие → шлюз в **одной транзакции** создаёт или находит
клиента, диалог и записывает сообщение → публикует событие в Redis → `api` рассылает его
по WebSocket всем, кто имеет право видеть этот диалог.

Дубли отсекает частичный уникальный индекс `(conversation_id, tg_message_id)`.
При конфликте вставки клиента по `telegram_id` — читаем существующего и продолжаем с ним.

**Исходящее.** `api` в одной транзакции пишет `messages` со статусом `queued` и строку в
`outbox` → публикует событие (интерфейс сразу показывает сообщение с часиками) → шлюз
забирает из `outbox` с блокировкой строки, отправляет через Telethon с нашим `random_id`,
записывает `tg_message_id` и статус `sent` → публикует событие.

**Отличие менеджера от юзербота.** `random_id` генерируем мы. Исходящее событие с неизвестным
нам `random_id` — это отправила воронка, пишем `author_kind = userbot`.

**Прочитано.** Событие `updateReadHistoryOutbox` переводит наши исходящие в `read`.

## 5. Конвенции бэкенда

- **SQLAlchemy 2.0 async**, `asyncpg`. Alembic для миграций. Сырой SQL — только в аналитике
  и поиске, где он честнее ORM.
- **Роутер тонкий.** Разбор запроса, вызов сервиса, отдача ответа. Вся логика — в `services/`.
- **Права проверяются в сервисе**, не в роутере и не во фронтенде.
  **Чужая сущность для менеджера — 404, а не 403.** 403 подтверждает, что запись существует.
- **Пагинация — курсорная** (`?cursor=&limit=`), не по номеру страницы. На 50 000 записей
  постраничность по смещению начинает тормозить.
- **Деньги в API** — целые копейки, поле называется `amount`. Форматирование — во фронтенде.
- **Ошибки** — единый формат `{"error": {"code": "...", "message": "...", "details": {...}}}`.
  `code` — машинный, `message` — по-русски, показывается пользователю.
- **Хеширование пароля** (bcrypt) уносится в пул потоков: в асинхронном приложении оно
  блокирует цикл событий, и один вход подвешивает весь сервер.
- **Каждое изменение данных пишет `event_log`** в той же транзакции.
- **Все ответы отдают `updated_at`**, изменение проверяет его на совпадение —
  защита от затирания чужой правкой.

### Аутентификация

Логин и пароль. Токен сессии в cookie: `HttpOnly`, `SameSite=Lax`, `Secure` в продакшене.
Срок 30 дней. Смена пароля и деактивация отзывают все сессии.
Блокировка после 5 неудач за 30 минут. Логин нормализуется до сравнения.

### WebSocket

`/api/v1/ws` с той же cookie. Сервер шлёт:

```json
{"type": "message.new",       "data": {"conversation_id": 1, "message": {...}}}
{"type": "message.updated",   "data": {"message": {...}}}
{"type": "conversation.updated", "data": {"conversation": {...}}}
{"type": "counters.updated",  "data": {"total": 38, "awaiting": 4, "awaiting_payment": 15}}
{"type": "deal.updated",      "data": {"deal": {...}}}
{"type": "notification.new",  "data": {"notification": {...}}}
{"type": "presence.updated",  "data": {"user_id": 3, "online": true}}
{"type": "account.status",    "data": {"account_id": 2, "status": "error", "reason": "..."}}
```

Клиент шлёт `{"type":"ping"}` каждые 25 секунд и `{"type":"viewing","conversation_id":N}` —
чтобы в шапке чата было видно, кто ещё здесь. При обрыве переподключается и **дозагружает
пропущенное запросом**, а не показывает молча устаревшее.

## 6. Конвенции фронтенда

- **React 19 + TypeScript, строгий режим.** `any` запрещён.
- **TanStack Query** — всё, что приходит с сервера. Никакого дублирования серверных данных
  в глобальном хранилище.
- **Zustand** — только состояние интерфейса (открытые панели, черновики полей ввода).
- **Tailwind + shadcn/ui.** Цвета и размеры — **только через токены**, произвольных значений
  в разметке нет.
- **Виртуализация** списков чатов, клиентов, оплат и переписки.
- **Формы** — react-hook-form + zod; схемы проверки повторяют серверные.
- **Ошибка обязана быть видимой.** Интерфейс **никогда** не подменяет ошибку демо-данными.
  В прошлой версии фронтенд при ответе «не авторизован» молча показывал моки, и всё
  «работало» — самый дорогой класс багов. Режим с демо-данными и боевой режим не имеют
  общего кода отката.
- **Каждый экран имеет четыре состояния:** загрузка (скелет), пусто, ошибка с кнопкой
  «повторить», данные. Экран без всех четырёх считается недоделанным.
- **Ни одной кнопки-обманки.** Элемент либо работает, либо его нет.

налезает друг на друга — сетку, отступы и типографику выстраиваем заново по шагу 4px.

### Раскладка

Один код, две раскладки, граница — **860px**.

Почему 860, а не 1024: на ноутбуке окно почти никогда не развёрнуто во весь экран,
а при увеличенном масштабировании экрана логическая ширина макбука падает ниже 1024.
С порогом 1024 пользователь на ноутбуке видел мобильную версию. При 860 две колонки
ещё помещаются (список 300 + рабочая область 560), а планшет в портрете (768)
корректно остаётся на мобильной раскладке.

- **Мобильная:** нижняя навигация из пяти вкладок (Чаты, Клиенты, Оплаты, Статистика,
  Профиль). Модальные окна выезжают снизу, закрываются крестиком и свайпом вниз.
- **Десктоп:** левый вертикальный рельс иконок → колонка списка → рабочая область →
  правая панель карточки.

## 7. Локальный запуск

```
make up      # поднимает всё: db, cache, storage, api, gateway, scheduler, web
make seed    # демо-данные: 2 руководителя, 5 менеджеров, 3 аккаунта, ~40 клиентов,
             # переписка за 3 месяца, ~30 сделок во всех статусах
make test    # pytest + vitest
make lint    # ruff, mypy, eslint, tsc
```

**Демо-данные и живой Telegram не смешиваются.** В режиме `DEMO_MODE=true` шлюз не
подключается к Telegram вообще. В прошлой версии смешивание дало лавину ложных срабатываний.

## 8. Продакшен

- Один сервер, Docker Compose, nginx + Let's Encrypt. Локация — решается отдельно.
- Фронтенд собирается **внутри образа** с боевым адресом API. Никаких готовых сборок
  с машины разработчика: в прошлой версии так сборка с моками уехала в продакшен.
- GitHub Actions: линт и тесты → сборка образов → выкатка по SSH. Откат — одной командой.
- Резервные копии базы каждый час в объектное хранилище, хранение 30 дней,
  восстановление проверяется, а не предполагается.
- Ключ шифрования сессий Telegram — в переменной окружения, не в репозитории и не в образе.

## 9. Порог для пересмотра

Возвращаемся к этому документу, когда наступит любое из:

- больше 50 подключённых аккаунтов — шлюз переезжает на отдельную машину;
- больше 50 млн строк в `messages` — плановое разрезание таблицы по месяцам;
- аналитика перестаёт укладываться в 2 секунды — реплика базы под чтение;
- появляются подписки или возвраты — раздел «следующие этапы» в `02-data-model.md`.
