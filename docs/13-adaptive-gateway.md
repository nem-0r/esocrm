# 13. Адаптивный шлюз: как распределяется мощность и что будет при апгрейде сервера

Этот документ — ответ на конкретный вопрос: если менять сервер (больше ядер, больше
памяти), нужно ли что-то пересчитывать руками, чтобы выдержать 25+ подключённых
аккаунтов Telegram и столько же (или больше) менеджеров одновременно. Короткий ответ —
нет, не нужно: число процессов шлюза, сколько аккаунтов каждый готов взять, и сколько
соединений с базой он для этого откроет — всё это система считает сама при каждом
старте, глядя на реальное железо контейнера. Ниже — что именно это значит и почему
это безопасно.

Технический контракт (что обязано быть верно в коде) — в `07-architecture.md` §1–2.
Здесь — развёрнутое объяснение и обоснование, для понимания «как это будет работать»
до того, как понадобится читать код.

---

## 1. Кто с кем связан: состав системы одним взглядом

```
                         ┌──────────┐
                         │  клиент  │  (браузер менеджера)
                         └────┬─────┘
                              │ HTTPS + WebSocket
                         ┌────▼─────┐
                         │  nginx   │  HTTPS, отдаёт статику фронтенда
                         └────┬─────┘
                              │
                    ┌─────────▼─────────┐
                    │        api        │  FastAPI: REST, WebSocket, права,
                    │  (2 процесса,     │  аналитика — всё, чем управляет
                    │   uvicorn)        │  менеджер и руководитель
                    └───┬────┬────┬─────┘
                        │    │    │
            ┌───────────┘    │    └───────────┐
            │                │                │
      ┌─────▼─────┐   ┌──────▼──────┐   ┌─────▼──────┐
      │ postgres  │   │    redis    │   │    S3      │
      │ (db)      │   │   (cache)   │   │ (storage)  │
      │ единый    │   │ живые       │   │ вложения,  │
      │ источник  │   │ события,    │   │ чеки,      │
      │ правды    │   │ команды в   │   │ материалы  │
      └─────▲─────┘   │  шлюз       │   └────────────┘
            │          └──────▲──────┘
            │                 │ pub/sub: команды и ответы
      ┌─────┴──────────────────┴─────┐
      │           gateway            │  Telethon: держит сессии Telegram,
      │  (N процессов, N — по ядрам) │  принимает и отправляет сообщения
      └───────────────────────────────┘
            │
      ┌─────▼─────┐
      │ scheduler │  APScheduler: сроки сделок, уборка мусора
      └───────────┘
```

Все стрелки, которые действительно важны для «выдержит ли нагрузку»:

- **Менеджер → `api`.** Открыть чат, отправить сообщение, посмотреть карточку клиента,
  выгрузить CSV — всё это НЕ трогает `gateway` напрямую. `api` читает и пишет в Postgres,
  публикует событие в Redis, `api` же (через WebSocket) мгновенно доносит его до всех
  открытых вкладок других менеджеров. Больше менеджеров работает одновременно — больше
  нагрузки на `api` и `db`, `gateway` эта нагрузка не касается вообще.
- **`api` → `gateway`.** Единственный путь — команда через Redis pub/sub (`app/core/command_bus.py`):
  «войди в аккаунт», «подтверди код», «пришли QR». Это узкий, редкий канал (человек нажимает
  кнопку «подключить» — не то, что происходит сотни раз в секунду), не место, где нагрузка
  может расти вместе с числом менеджеров.
- **`gateway` → `db`/`redis` напрямую**, без похода через `api`: принял сообщение от
  Telegram — сразу записал в базу и опубликовал событие; должен отправить — сам забрал
  из очереди `outbox` и отправил. `api` в этом пути не участвует, только слушает то же
  самое событие в Redis, чтобы разослать по WebSocket.

Вывод из этой картинки: у роста числа **юзерботов** и роста числа **менеджеров** — РАЗНЫЕ
узкие места. Первое давит на `gateway`, второе — на `api`+`db`. Ниже — про оба.

## 2. Как «мощность» распределяется внутри шлюза

### 2.1. Раньше и сейчас

До этой правки число процессов `gateway` задавалось в docker-compose руками (`deploy.replicas`)
— число, верное ровно для одного конкретного сервера. Апгрейд VPS требовал вручную
пересчитать и переписать файл, а забыть это сделать — значит либо не использовать новые
ядра, либо (при заниженном числе вручную) недодать шлюзу ресурсов, которые сервер реально
может дать.

Теперь контейнер `gateway` один-единственный, а сколько **процессов операционной системы**
внутри него — решает код при каждом старте:

```python
# app/gateway/topology.py
def worker_count() -> int:
    return max(1, detected_cores() - 1)   # одно ядро — в запас под api/db/scheduler
```

`detected_cores()` спрашивает не «сколько ядер у сервера вообще», а «сколько ядер видно
ИМЕННО ЭТОМУ контейнеру» (`os.sched_getaffinity`) — если когда-нибудь контейнеру ограничат
доступные ядра через cgroup, число подстроится и под это, а не только под реальный
апгрейд железа.

Наглядно, на измеренных числах:

| Сервер | Ядер видно контейнеру | Процессов шлюза (ядра − 1) |
|---|---|---|
| нынешний Timeweb Cloud (прод) | 4 | 3 |
| Mac разработчика (Docker Desktop) | 8 | 7 |
| гипотетический апгрейд до 16 ядер | 16 | 15 |

Апгрейд сервера = **перезапуск контейнера** увидел новое число ядер сам. Ничего в
конфигурации трогать не нужно.

### 2.2. Процессы, не потоки — почему это важно

Внутри Python один процесс не может по-настоящему занять два ядра одновременно (GIL).
Поэтому «параллелизм» здесь — это буквально N отдельных процессов операционной системы
(`multiprocessing`, режим `spawn`), каждый из которых — точная копия того кода, что раньше
был единственной точкой входа шлюза. Ни один из них не знает, что рядом работают такие же:
они не координируются между собой напрямую, а безопасно делят аккаунты через базу —
следующий пункт.

### 2.3. Аренда аккаунтов: как N процессов не хватают один и тот же аккаунт разом

Каждый процесс, независимо от остальных, раз в 10 секунд:

1. Продлевает свою «отметку живости» и аренду уже взятых им аккаунтов на 30 секунд.
2. Если держит меньше своего лимита — пытается забрать свободные аккаунты
   (`SELECT ... FOR UPDATE SKIP LOCKED` — специальный режим Postgres: если строка уже
   заблокирована другим процессом, эта просто пропускается, а не ждёт в очереди).

`SKIP LOCKED` — это ровно то, что гарантирует: два процесса физически не могут забрать
один и тот же аккаунт одновременно, сколько бы их ни было — 3, 7 или 31. Проверено не
только по чтению кода: локально запускали 7 процессов, «убивали» один из них по-настоящему
(`kill -9`) и убеждались, что аккаунты, которые он держал, подхватывает сосед, а супервизор
поднимает замену за секунды — без дублирования и без «зависших» аккаунтов.

Если процесс пропал совсем (упал, не просто временно занят) — аренда протухает через
30 секунд сама, и аккаунт достаётся любому живому соседу. На практике до этого обычно
не доходит: супервизор контейнера следит за своими процессами и поднимает замену за
5 секунд, не дожидаясь протухания.

### 2.4. Самоограничение по нагрузке хоста — вторая ось адаптации

Число процессов — это про то, сколько работы можно делать ПАРАЛЛЕЛЬНО. Отдельный
вопрос — сколько НОВЫХ аккаунтов безопасно брать прямо сейчас, если сервер и так занят
(например, у нескольких аккаунтов разом идёт крупная подгрузка истории). Здесь работает
второй, независимый механизм (`app/gateway/load.py`): каждый процесс перед тем, как
взять новые аккаунты сверх уже удержанных, смотрит на загрузку процессора **и** занятость
памяти хоста прямо сейчас:

- свободно (занято меньше 60%) — берёт до полного лимита;
- занято (больше 90% хотя бы по одному из двух показателей) — новых пока не берёт,
  но уже взятые не бросает — оборвать отправку на полпути хуже, чем временно не расти;
- между 60% и 90% — плавно, пропорционально свободному запасу.

Порог — **доля**, а не абсолютное число: одна и та же логика верна и на сервере с 4 ГБ
памяти, и на сервере с 64 ГБ, без какой-либо перенастройки при апгрейде — апгрейд просто
отодвигает момент, когда доля вообще приблизится к порогу.

### 2.5. Соединения с базой — третья ось, о которой легко забыть

Есть тонкость, которую первая версия этой переделки не учла (нашли и исправили при
проверке): у каждого процесса — свой собственный пул соединений с Postgres. Если бы его
размер был фиксирован (как раньше — 10 соединений на процесс), апгрейд сервера с 4 до
16 ядер увеличил бы число процессов шлюза с 3 до 15 — и суммарное число соединений с
базой выросло бы впятеро, никем не спланированным образом, вплоть до исчерпания лимита
самого Postgres.

Исправлено так же, автоматически: `DB_POOL_SIZE`/`DB_MAX_OVERFLOW` (по умолчанию 10/20)
для шлюза — это теперь общий **бюджет на контейнер**, который код сам делит на число
процессов:

| Сервер | Процессов шлюза | Пул на процесс | Суммарно (пул + разовый запас) |
|---|---|---|---|
| прод сейчас (4 ядра) | 3 | 3 + 6 | ≈ 27 |
| Mac разработчика (8 ядер) | 7 | 2 + 2 (упёрлось в минимум) | ≈ 28 |
| гипотетические 16 ядер | 15 | 2 + 2 (минимум) | ≈ 60 |

Суммарное число остаётся в разумных пределах при любом железе — не потому что кто-то
угадал число заранее, а потому что оно каждый раз считается заново от того же бюджета.

## 3. Прямые ответы на вопросы

### Ускорит ли это подгрузку истории чатов при добавлении новых юзерботов?

**Для нескольких аккаунтов одновременно — да.** Раньше все аккаунты в одном процессе
конкурировали за одно и то же процессорное время (GIL). Теперь на 4-ядерном проде три
аккаунта, у которых одновременно идёт подгрузка большой истории, могут делать это на
трёх разных ядрах по-настоящему параллельно, а не по очереди.

**Для скорости ОДНОГО конкретного аккаунта — нет**, и это не про нашу архитектуру:
скорость, с которой Telegram отдаёт историю ОДНОМУ аккаунту, упирается в собственные
лимиты частоты запросов и сетевую задержку на стороне Telegram, а не в то, сколько ядер
свободно на нашем сервере. Больше процессов = больше аккаунтов грузятся параллельно,
но не быстрее сам по себе один аккаунт.

### Выдержит ли это, когда одновременно работает много менеджеров?

Здесь нужно разделить два слоя, потому что менеджеры нагружают ДРУГУЮ часть системы,
не `gateway` (см. диаграмму в §1):

- Открытые вкладки, переписка, статистика, экспорт — всё это `api` + Postgres + Redis.
  `gateway` про это вообще не знает и не участвует.
- `api` сейчас — **единственное место, которое НЕ адаптируется автоматически**: 2 процесса
  uvicorn, привязанные к явному пределу `cpus: 2.0` в `docker-compose.prod.yml`. Эта пара
  чисел согласована между собой (примерно процесс на ядро в пределах лимита), но не
  вырастет сама, если увеличить лимит `cpus` при апгрейде сервера — число процессов нужно
  будет увеличить вместе с ним руками.
- Postgres тоже не бесконечен: у него есть общий лимит подключений
  (`max_connections`, обычно 100+ на типичном тарифе). `api`, `gateway` и `scheduler`
  вместе должны укладываться в этот лимит — с новым делением бюджета шлюза (§2.5) это
  теперь предсказуемо посчитать.

**Рекомендация**, если апгрейд сервера делается в том числе ради большего числа
менеджеров одновременно: увеличивать лимит `cpus` для `api` и число `--workers` **вместе**,
в одной пропорции (например, было 2/2.0 — при апгрейде до условных 4 свободных ядер под
api разумно поставить `cpus: "4.0"` и `--workers 4`). Довести и эту пару до полностью
автоматического пересчёта, как уже сделано для шлюза, — следующий кандидат на такую же
переделку, отдельная, самостоятельная задача (потребует такого же деления бюджета
соединений с базой, что и здесь для шлюза, — иначе получится ровно та же ошибка,
которую только что нашли и исправили).

### Какая конфигурация лучше всего для нашего сервера?

Раньше на этот вопрос был бы ответ вида «конкретное число реплик под конкретный сервер».
Теперь ответ другой: **само число процессов шлюза выбирать не нужно** — оно считается
каждый раз заново. То, что реально осталось настраивать руками — три величины, и у всех
трёх есть безопасные значения по умолчанию:

| Настройка | Что означает | Значение по умолчанию | Когда трогать |
|---|---|---|---|
| `GATEWAY_CAPACITY` | сколько аккаунтов один процесс шлюза готов держать разом | 15 | почти никогда — при 3 процессах это уже 45 аккаунтов, с запасом на 25+ |
| `DB_POOL_SIZE` / `DB_MAX_OVERFLOW` | общий бюджет соединений с базой на контейнер шлюза (делится на число процессов, §2.5) | 10 / 20 | если Postgres выдаёт мало `max_connections` — уменьшить; если апгрейд сервера сильно расширил число процессов и в логах видно нехватку пула — увеличить |
| `memory: 1536M` для `gateway` в `docker-compose.prod.yml` | страховочный потолок памяти на контейнер целиком | 1.5 ГБ | при апгрейде сервера можно поднять пропорционально общей памяти — это не точный бюджет, а именно страховка от аварийного разрастания |

Для цели «25+ подключённых аккаунтов и не меньше менеджеров» текущие значения по
умолчанию уже с запасом покрывают её на нынешнем 4-ядерном сервере (3 процесса × 15 =
45 мест) — и продолжат покрывать после апгрейда без единой правки.

## 4. Что было проверено, а не только продумано

Помимо чтения кода, до включения в прод список того, что проверено вживую на локальном
окружении:

- Автоопределение действительно возвращает разные числа на разном железе (8 на Mac,
  4 на реальном проде — проверено по SSH).
- 7 процессов на 8-ядерной машине — это реально 7 разных процессов ОС (`docker top`
  подтвердил разные PID), а не 7 задач `asyncio` внутри одного.
- Убийство одного процесса (`kill -9` по PID изнутри контейнера) не оставляет
  «зависших» аккаунтов: сосед подхватывает, супервизор поднимает замену за ~5 секунд,
  зомби-процессов не остаётся.
- Штатная остановка контейнера (`docker compose stop gateway`) укладывается в секунду
  и корректно освобождает аренду всех аккаунтов (было — до находки и исправления
  бага с обработкой сигналов — до 30 секунд с потерянной арендой).
- Отдельным проходом (независимая ролевая проверка «найти проблему в этой схеме»)
  нашли и исправили ещё три вещи до того, как они стали проблемой в проде:
  обработчики сигналов супервизора теперь ставятся ДО запуска процессов (иначе
  быстрый перезапуск контейнера мог оставить часть процессов без присмотра);
  деление бюджета соединений с базой (§2.5); уборка мёртвых строк учёта процессов
  в базе — раз в час, чтобы служебная таблица не росла бесконечно при частых
  заменах процессов.
- Полный набор автоматических проверок (`make verify`, 647 пунктов — переписка,
  сделки, права, аналитика, экспорт и это в том числе) проходит без единой ошибки
  после всех перечисленных правок.

## 5. Порог для пересмотра

Возвращаемся к этому документу, когда наступит любое из:

- api переводится на такое же автоматическое определение числа процессов, как шлюз
  (см. рекомендацию в §3) — тогда бюджет соединений с базой нужно будет пересчитать
  для api так же, как здесь для gateway;
- шлюз действительно переезжает на отдельную от api/db машину (порог — 50+ аккаунтов,
  `07-architecture.md` §9) — тогда «одно ядро в запас» перестаёт быть нужным резервом,
  можно отдавать шлюзу все ядра его собственной машины;
- на проде реально понадобилось больше 45 одновременно подключённых аккаунтов —
  тогда `GATEWAY_CAPACITY` стоит поднять явно, а не полагаться на запас по умолчанию.
