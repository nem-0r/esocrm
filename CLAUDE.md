# tg_crm — CRM для эзотерических услуг с перепиской в Telegram

**Это переписывание с нуля.** Предыдущая версия — «Astra CRM» в `/Users/mac/crm` — была доведена
почти до продакшена и остановлена. Здесь строим заново: продуманная архитектура, новая модель
данных, новый дизайн (Miro). Код старой версии **не переносим**, знания и грабли — переносим.

## Что за продукт (коротко)

CRM для компании, продающей эзотерические услуги (таро, астрология, практики). Клиенты пишут
в личные Telegram-аккаунты, менеджеры ведут переписку **прямо из CRM** через **MTProto (Telethon),
не Bot API** — потому что общение идёт от личных аккаунтов, а не от бота. Это фундамент продукта.
Вокруг переписки: карточки клиентов, сделки и платежи, воронка продаж, SLA-контроль скорости
ответа, аналитика по менеджерам и продуктам. Роли: **admin / manager / observer**.

Подробный перенос знаний → **`docs/00-context.md` (читать первым)**.

## Как работать с пользователем

- Отвечать **по-русски**.
- Пользователь не разработчик. Объяснять архитектуру и «как это будет работать» **до написания
  кода**, до полного понимания. Технические решения делегирует («ты тимлид с 10-летним опытом»),
  но финальное решение принимает он.
- Главный критерий качества — **«работает с первого запуска, без багов»**.
- **Ни одной кнопки-обманки.** Если элемент есть в UI — он работает. Заглушка вместо действия
  считается дефектом, а не «пока так».
- Ценит детальные планы и разбор рисков заранее, а не по факту поломки.

## Порядок работы в этом проекте

1. Пользователь складывает актуальные материалы в `docs/` (данные, схемы, модель данных,
   бизнес-правила, выгрузку из Miro).
2. Разбираем и уточняем требования → `docs/03-business-rules.md`.
3. Проектируем архитектуру и модель данных, фиксируем выбор → `docs/05-decisions.md`.
4. Только после утверждения — код: бэкенд и фронтенд.

Не начинать писать код, пока шаги 1–3 не закрыты по конкретному куску функциональности.
